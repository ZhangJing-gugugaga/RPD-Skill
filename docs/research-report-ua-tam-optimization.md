# 深度研究报告：Understand-Anything 与 TencentDB-Agent-Memory 对 RPD-skill 的优化启示

## 研究背景与目标

用户（张敬）希望把 RPD-skill 从"项目状态机"升级为"任何项目生命周期的万能管理 skill"。RPD-skill v2 已确立 code-map 双层导航、红线机检、三级信任与决策日志等机制，但其能力边界能否支撑"万能管理"这一更宏大的目标，需要外部参照系的验证与启发。

为此，本报告深度调研两个 GitHub 开源仓库：**Egonex-AI/Understand-Anything**（代码理解图谱，将任意代码库转为可提交、可增量的结构化知识图谱）与 **TencentCloud/TencentDB-Agent-Memory**（智能体记忆治理，提供 L0-L3 分层记忆、混合检索与资产化治理）。本报告逐一拆解两仓库的核心机制，对照 RPD v2 现状盘点差距，提炼可落地的增量需求池，并给出面向"万能管理 skill"的架构演进方向，最终分析它们对 RPD-skill 的优化启示。

研究目标有三：其一，验证 RPD v2 已吸收的设计思想是否正确；其二，定位尚未覆盖能力的本质原因；其三，给出风险受控的下一步迭代与长期演进路线。若专家团队无法在本报告中明确用户需要为 skill 增加哪些内容，将在报告末尾以 grill-me 形式向用户追问（见结论章"面向用户的开放问题"）。

## 研究对象与方法

本报告采用"机制拆解 → 现状盘点 → 增量需求 → 架构演进"的四段递进方法，正文分为五章，逻辑逐层推进：

1. **机制拆解**：对两仓库按其官方文档、README、技术拆解与论文进行结构化拆解，提取可迁移的设计资产（第 1、2 章）。
2. **现状盘点**：以 RPD v2 内部技术规格为权威基准，将两仓库的 12 个启发点与 R-01~R-18 需求池逐项比对，形成覆盖/半覆盖/未覆盖矩阵与四类差距归因（第 3 章）。
3. **增量需求**：按"可即时承接 / 需改造适配 / 超出当前范围"三分法，将未覆盖与半覆盖的增量项汇入新增需求池 R-19~R-29，并归入 I4（P1）主线或 parking-lot 观察（第 4 章）。
4. **架构演进**：收敛为"项目级记忆 + 项目级图谱 + 经验资产化"三支柱架构与三阶段落地路径（第 5 章）。

**来源与方法局限说明**：正文论据以两仓库的官方文档、README、技术拆解与论文为主；少量指标来自第三方评测或媒体转引。凡涉及量化数据（如 Star 数、Token 节省比例、影响依赖数等），正文均标注其时效与"官方自报 / 第三方转引"属性，相关数字应视为方向性参考而非定论，不可直接用于对外承诺。

## 第 1 章 Understand-Anything 核心机制拆解与可迁移设计

**本章论点**：Understand-Anything 的核心不是"可视化"本身，而是「结构确定性 + 语义灵活性」的混合分析架构与「JSON 化、可提交、可增量」的图谱产物设计。这两点分别对应 RPD v2 的 code-map 双层导航（R-10 兼容读取）与 PRD 变更影响分析，是可迁移性最强的设计资产。

#### 1.1 Tree-sitter 确定性分析 + LLM 语义理解：结构层为何不让 LLM 重复解析

Understand-Anything 将代码理解拆成两个正交层（[1]）：**Tree-sitter 承担确定性结构层**——把源码解析为具体语法树，提取 imports/exports、函数/类定义、调用点、继承关系等结构性事实，同一份代码永远产出同一结果，可复现、可审计，同时作为指纹检测增量更新的基础；**LLM 承担语义层**——读取解析后的结构骨架与原始源码，生成解析器做不到的内容：纯英文摘要、标签、架构分层归属、业务领域映射、引导式讲解（[2]、[3]）。

设计者给出的理由很直白：**用 LLM 做结构提取是浪费且不可靠的**——同一个 import 语句两次运行可能被解析出不同结果；**用静态分析做语义理解是不可能的**——没有解析器能告诉你"这段代码代表用户登录流程"（[3]）。这正是"结构层可复现、语义层捕捉意图"分工的由来。

**对 RPD 的启发**：RPD v2 的 code-map 双层导航（router.json 层1 ≤3k token 常驻 + code-map.json 层2 按需单条 ≤300 token）天然适配这一分工——**router 层应当是确定性结构摘要**（文件树、模块依赖、入口点，可由解析器/脚本生成、可机检、可复现），**code-map 层承载语义摘要**（每个模块是干什么的、业务意图）。红线机检（commit hash + fingerprint）在概念上正是 Tree-sitter 指纹思想的工程化落地：用确定性的哈希/指纹判断"什么变了"，语义层才需要增量刷新。

#### 1.2 七阶段多 Agent 流水线：阶段化分工与中间产物

/understand 命令将全量分析组织为 7 个阶段（**5 个专职 Agent + 编排器 SAVE 收尾**）：Phase 1/4/5/6 各派发一个专职 Agent 并产出独立的中间 JSON 文件，Phase 2-3 共用 file-analyzer，Phase 7 的 SAVE 由编排器执行——写入最终 knowledge-graph.json 与 meta.json、清理 intermediate，不派发 Agent（[4]、[5]）。需要说明的是，仓库 agent 表跨全部命令合计 7 个角色——除上述 5 个外，另含 /understand-domain 的 domain-analyzer 与 /understand-knowledge 的 article-analyzer（[1]）。

| 阶段 | Agent | 产出物 |
|---|---|---|
| 1 | project-scanner | 文件清单、语言/框架检测 |
| 2-3 | file-analyzer（并行 5 并发/20-30 文件一批） | nodes/edges，扫描阶段预解析 importMap 避免重复推导 |
| 4 | architecture-analyzer | layers.json（架构分层） |
| 5 | tour-builder | tour.json（按依赖拓扑排序的学习路径） |
| 6 | graph-reviewer | review.json（引用完整性校验 + 自动修复） |
| 7 | SAVE | knowledge-graph.json + meta.json，清理 intermediate |

**来源版本说明**：file-analyzer 的并发与批大小在两份来源中存在版本差异——GitHub README 记为「5 并发、20-30 文件一批」，LobeHub v1.0.1 SKILL.md 记为「5-10 文件一批、最多 3 并发」；本文表格按 GitHub README 取值，实际参数以所用版本为准（[4]）。

两个工程细节值得注意：其一，**增量更新时架构分析仍全量重跑**，因为分层归属会随文件变化移动——不是所有阶段都可增量（[4]）；其二，错误处理哲学是"**ALWAYS save partial results — a partial graph is better than no graph**"（部分结果优于无结果），单阶段失败重试一次后跳过，但失败必须在最终报告中可见，绝不静默丢弃（[4]）。

**对 RPD 的启发**：RPD 现有 12 个 stdlib 脚本可按"扫描 → 抽取 → 架构 → 校验 → 装配"组织为阶段化流水线，每阶段独立产物文件（如 intermediate/*.json），阶段间解耦、可单独重跑；对"哪些阶段可增量、哪些必须全量"（如架构分层）做显式标注，避免错误地全量缓存。

#### 1.3 knowledge-graph.json：JSON 化可提交复用 + 指纹增量更新（对应 R-10）

图谱产物是结构化的 typed directed graph，顶层为 `version + project（含 gitCommitHash）+ nodes + edges + layers + tour`；节点 16 种（file/function/class/module/concept + 非代码 config/service/endpoint 等 + 领域 domain/flow/step），边 35 种、8 大类别（结构/行为/数据流/依赖/语义），并带权重约定（contains 1.0 / inherits·implements 0.9 / calls·exports 0.8 / imports 0.7 / depends_on 0.6 / tested_by 0.5，其余默认 0.5；权重约定见 [4] 的 Edge Weight Conventions），加载时用 Zod 4 层校验保证类型安全与引用完整性（[5]）。

关键收益有两条：
1. **JSON 化可提交复用**：图谱是纯 JSON，commit 一次、团队成员即可跳过整条生成管线直接查询（无 Claude Code 者可用 npx viewer 打开）；超过 10MB 建议 git-lfs 管理（[6]）。
2. **指纹增量更新**：默认只重分析变更文件；过期检测用 **git commit hash + 结构指纹**双重机制（[5]、[1]）。

在 token 成本上，第三方分析引用同类项目数据：把项目一次性压缩成 JSON、之后所有交互查图谱而非重读源码，"code-review-graph 类项目"报告评审任务节省 6.8× token、日常编码节省 49×（[7]）——此为第三方转引对比数据，非官方基准，但方向上印证"扫描一次、复用多次"的哲学。

**对 RPD 的启发（直接命中 R-10）**：RPD v2 已定"R-10 兼容读取 understand-anything 的 knowledge-graph.json（只读复用）"——基于以上机制，RPD 可把该 JSON 作为项目理解快照的**标准输入**：结构层（nodes/edges/layers）直接映射 code-map 的 router 层，语义层（summary/domain）映射 code-map 层2，无需自己重跑全量分析；commit hash + 指纹即可判断快照是否过期。

#### 1.4 /understand-diff 与 /understand-domain：需求↔代码双向映射支撑 PRD 变更影响分析

/understand-diff 把 git diff 映射到图谱做**图级影响分析**：`buildDiffContext` 区分 changedNodes（filePath 匹配 + 包含的函数/类节点）、affectedNodes（1-hop 边连接的依赖者）、affectedLayers、unmappedFiles；采用 grep 定向读取而非整图载入上下文；输出结构化报告（Changed / Affected Components、Affected Layers、Risk Assessment——基于节点 complexity、跨层边数与 blast radius），并写 diff-overlay.json 供 Dashboard 高亮（[8]、[9]）。第三方演示场景显示：改一个数据库模型字段，可追踪到 47 个直接依赖、218 个传递依赖、影响 4 个业务域并按 Critical/High/Medium/Low 分级——该数字为 explainx.ai 对官方 README 演示场景的转述，属演示案例而非实测基准（[10]）。

/understand-domain 则反向打通：domain-analyzer 读取全部节点的语义摘要做聚类与命名，把技术符号（UserController.ts / JwtMiddleware）映射为业务语言（注册与登录 / 权限校验），形成非技术人员可读的横向视图（[3]）。

**对 RPD 的启发**：PRD 变更影响分析 = 需求概念（domain/flow/step 节点）与代码模块（file/function/class 节点）的**双向映射**。改 PRD 的某个需求时，沿 domain → flow → file 边定位受影响的代码模块并做风险分级（对应 diff 的 blast radius 逻辑）；反向地，代码改动时沿同一图谱提示"这条 PRD 需求是否受影响"。这与 RPD"需求诊断 → PRD → code-map"的闭环天然衔接。

#### 小结

Understand-Anything 对 RPD 的四个可迁移设计：① **结构/语义分层**（Tree-sitter 确定性 + LLM 语义）对应 code-map 双层导航，router 层必须机检可复现；② **七阶段流水线 + 中间产物 + 部分保存**对应 12 脚本的编排原则；③ **JSON 图谱可提交复用 + commit hash/指纹增量**直接命中 R-10，让 RPD 免于重复全量理解；④ **diff 图级影响分析 + 业务领域视图**为 PRD 变更影响分析提供"需求↔代码"双向映射范式。

### 关键发现

- **结构/语义分层是首要可迁移设计**：Tree-sitter 确定性结构层（可复现、可机检、可指纹增量）与 LLM 语义层（捕捉业务意图）的混合架构，直接对应 RPD v2 code-map 双层导航——router 层必须是确定性摘要，code-map 层承载语义摘要。
- **阶段化流水线是可落地的工程范式**：7 阶段（5 专职 Agent + 编排器 SAVE 收尾）+ 独立中间 JSON + 部分保存哲学，为 RPD 12 脚本编排提供"扫描→抽取→架构→校验→装配"模板；架构分层阶段必须全量重跑，不可盲目增量缓存。
- **JSON 图谱可提交复用直接命中 R-10**：knowledge-graph.json 的"commit 一次、复用多次 + commit hash/指纹增量"使 RPD 可将其作为项目理解快照的标准输入，免于重复全量分析。
- **diff 图级影响分析 + 业务领域视图提供 PRD 双向映射范式**：需求概念（domain/flow/step）与代码模块（file/function/class）沿图双向映射，支撑 PRD 变更影响分析与代码改动反查需求。

## 第 2 章 TencentDB-Agent-Memory 核心机制拆解与可迁移设计

### 论点

RPD 目前面临的核心矛盾是"跨会话状态"的沉淀方式过于扁平：决策日志（decisions.md）与活动上下文（active-context.md）将所有信息等价堆叠，缺少粒度分层与按需暴露机制。腾讯云开源的 TencentDB-Agent-Memory（以下简称 TAM）提供了业界少见的完整答案——L0-L3 分层记忆 + 异步蒸馏流水线 + 分层检索 + 四类资产治理（[11]）。其设计哲学可概括为：**"低层留证据、高层留结构，知识只在真正需要时才进入上下文"**（[12]），这与 RPD v2 已定的 code-map 双层导航（router.json 常驻 + code-map.json 按需单条）在思想上同源，但 TAM 在记忆层与治理层走得更远，是 RPD 跨会话状态升级的直接参照系。

### 论据一：L0-L3 分层记忆与"提取-聚合-蒸馏"异步流水线

TAM 将对话首先保存为 L0 原始对话层（全量保留，用于核实措辞、时间戳与来源），由异步流水线逐层提炼：L1 原子记忆层自动抽取事实、偏好、约束与阶段结论；L2 场景归纳层按项目/任务聚合为知识块；L3 画像层持续蒸馏出稳定的长期画像（[13]）。官方 README 明确其蒸馏路径为 L0 Conversation → L1 Atom → L2 Scenario → L3 Persona，层与层之间通过"提取-聚合-蒸馏"管道连接，任何一层都可独立升级或替换（[11]）。一个关键工程决策是：**底层 L0/L1 存数据库保证检索稳定，高层 L2/L3 存 Markdown 保证人可读可调**，使记忆系统成为可调试的白盒（[12]）。

**映射分析**：RPD 当前的 decisions.md + active-context.md 正是典型"扁平结构"——决策细节、项目背景、进行中状态全部挤在同一文件，检索与注入成本随项目复杂度线性上升。可迁移设计为四层：L0 = 原始扫描输出/对话证据（仅留指纹或路径引用，不常驻）；L1 = 原子决策/需求事实（每条可独立引用，如"用户要求 TypeScript"）；L2 = 场景块（PRD 生成场景、接手半成品场景、继续开发场景各自的上下文包）；L3 = 项目画像（长期稳定基线：技术栈、红线、团队约定）。其中"高层存 Markdown、低层存证据引用"的分层原则与 RPD v2 产品层 md + 代码层 json 的分层落点天然契合。

### 论据二：分层检索与渐进式暴露机制

TAM 的生成与检索都是分层式的：**平时 L2/L3 提供快速上下文引导，需要具体事实时通过 BM25 + 向量检索 + RRF（Reciprocal Rank Fusion）混合检索回退到 L1/L0 精确召回**（[11]）。为防上下文膨胀，检索结果受三重预算限制：条目数上限、字符预算、超时限制（[14]）。其工程体现是"知识不整体注入，而是按需调用"：Agent 先通过 `/v3/tools/list` 发现能力，再用 `/v3/tools/call` 读取相关页面/源码/影响路径（[14]）。官方评测显示，作为 OpenClaw 插件接入后，Token 消耗最高节省 61.38%，任务通过率相对提升 51.52%，PersonaMem 准确率从 48% 提升至 76%（[13]）。

**映射分析**：RPD v2 的 code-map 双层导航（router.json 层1 ≤3k token 常驻 + code-map.json 层2 按需单条 ≤300 token）已具备"渐进式暴露"雏形，但缺失两个关键件：一是**回退检索**——当常驻索引不足以回答细节问题时，应能按关键词/向量回退到 L1/L0 原始证据；二是**预算上限**——RPD 尚无"本任务允许注入的上下文上限"硬约束，PRD 生成时若将所有场景块全量注入，仍会重现上下文膨胀。建议为 .rpd/ 引入条目数+字符数双预算，并让 L2 场景块成为 PRD 生成的默认供给单位，仅当需要追溯决策依据时才展开 L1/L0。

### 论据三：四类记忆资产与元数据治理模型

TAM 将可复用经验归纳为四类资产：Chat Memory（偏好/事实/决策/交互历史）、Skill（从对话与工具调用提取的可复用流程，含版本、资源文件、触发边界、执行步骤、验证规则——"不止是提示词片段"）、LLM-Wiki（文档转结构化页面+链接图，受 Karpathy LLM Wiki 理念启发）、CodeGraph（代码符号/文件/调用关系/影响路径索引）（[14]）。官方 README 未显式采用 identity/scope/trust/lifecycle/governance 五维命名，但功能上均有支撑：所有权经 Owner 追踪（identity）、可见性分 private/team/restricted/agent 四档（scope）、Skill 共享前需评审（trust 的最接近实现）、版本/状态/使用计数统一管理（lifecycle）、全局 System Admin + 团队 Admin/Member 双层角色（governance）（[14]）。

**映射分析**：RPD 的 PRD 模板、评审清单、诊断流程本质上就是"Skill 类资产"，但目前只是散落的脚本与文档，缺少**版本、触发边界、验证规则、作用域绑定**四要素。TAM 的 Skill 提取实践给出了工程化路径：证据切分 → 候选抽取 → 作用域绑定（补充 Owner/Team/Repo/Branch/Version/ACL）→ 验证后升级（未验证的轨迹先作低权重背景，能经受测试/提交/Review 的内容才升级为共享 Skill）（[15]）。这直接对应 RPD 的"红线机检 + 三级信任（verified/unverified/stale）"——RPD 已有信任分级雏形，可进一步把"评审通过的 PRD 模板/诊断流程"升级为带版本与验证规则的资产化 Skill。

### 论据四：工程化设计——Fixed Binding、ACL、MemoryProxy 与资产归属

TAM 的权限与接入设计是区分于普通向量库的关键：**Memory Hub 采用 Fixed Binding + ACL 先按 Team/User/Agent/可见性缩小权限范围，再基于当前查询检索**——"无权限的资产不会进入候选池，而不是召回后再删除"，符合 NIST 零信任的最小权限原则（[16]）。新 Chat Memory 和 Skill **默认私有**，"共享是显式动作，不是默认泄露"（[14]）。任务期间**可锁定资产版本**，避免同一任务前后读到不一致的规则；资产生命周期支持新增/Review/发布/Fork/合并/降权/过期/锁定/删除（[16]）。接入侧采用 MemoryProxy 零代码方案：把 Agent 的 base URL 指向 Proxy 即可，无需插件、钩子或 MCP 服务，已适配 Claude Code、Codex、CodeBuddy、WorkBuddy、DeepSeek Harness、Hermes、OpenClaw（[17]、[14]）。记忆资产与 Agent 框架解耦，切换框架只需"重新装备"而非"重新训练"（[14]）。开源 80 天 GitHub Star 超 15000、多次登顶 Trending，反映社区对其"治理优于检索"路线的认可（[18]）。

**映射分析**：RPD 的跨项目隔离（.rpd/ 每项目一份）与"需求基线锁定"可借鉴三点：一是**先过滤后检索**——RPD 的代码层 json 应按项目/模块 ACL 过滤后再供给，而非全量扫描；二是**基线版本锁定**——需求冻结后锁定基线版本，与红线机检的 commit hash 机制结合，防止跨会话读取到不一致的需求；三是**资产跟项目走而非跟 Agent 走**——RPD 的 .rpd/ 已天然按项目落点，应保持"资产归属项目/团队"而非某个会话，确保换人换会话可持续。

### 争议与局限（多元观点）

需要审慎对待的三点：其一，**PersonaMem 48%→76% 为官方自报数据**，目前无独立第三方复现，业界评测建议"视为方向性指标而非定论"（[19]）；其二，**CodeGraph 目前优先支持公开 HTTPS 仓库，私有仓库与 SSH 凭据支持仍在完善**，这对多数真实团队是当前最大短板（[19]、[20]）；其三，**记忆路由仍偏手动**，自动"把正确记忆送到正确 Agent"尚在迭代，社区用户反馈记忆捕获仍偏被动（[19]）。

### 小结

TAM 给 RPD 的核心启示不是"引入一个记忆数据库"，而是四层可迁移设计：(1) 跨会话状态从扁平文件升级为 L0-L3 分层落点（证据/原子/场景/画像）；(2) 上下文供给从全量注入升级为"常驻引导 + 按需回退 + 三重预算"；(3) 经验资产从散落脚本升级为带版本/触发边界/验证规则的 Skill 类资产；(4) 隔离与锁定从目录约定升级为"先过滤后检索 + 基线版本锁定 + 资产跟项目走"。RPD v2 的 code-map 双层导航、三级信任、.rpd/ 分层落点已站在正确方向上，本章机制为其补齐了"记忆分层 + 预算治理"两块拼图。

### 关键发现
- 发现1：TAM 将记忆按证据→原子→场景→画像四层异步蒸馏，"低层存证据、高层存结构"，RPD 的 decisions.md + active-context.md 扁平结构应参照改造（[12]、[11]）
- 发现2：分层检索"L2/L3 快速引导 + BM25/向量/RRF 回退 L1/L0 + 三重预算上限"是防上下文膨胀的关键，RPD 已有双层导航但缺回退检索与预算硬约束（[14]）
- 发现3：四类资产中 Skill 最有迁移价值——RPD 的 PRD 模板/评审清单/诊断流程应补版本、触发边界、验证规则、作用域绑定四要素（[15]）
- 发现4：Fixed Binding+ACL 的"先过滤后检索"、默认私有、版本锁定、资产跟 Team 走，直接对应 RPD 的跨项目隔离与需求基线锁定需求（[16]、[14]）
- 发现5：官方评测数据（Token -61.38%、PersonaMem 48%→76%）为自报，业界建议作方向性参考而非定论（[19]）

## 第 3 章 RPD v2 现状盘点与差距分析：R-01~R-18 需求池对应关系

**本章论点**：RPD v2 已把两仓库启发点中"确定性结构 + 语义摘要、JSON 快照可提交、指纹增量、渐进式暴露"四条核心设计吸收进 code-map 双层导航与红线机检；但"图级影响分析、业务领域映射、分层记忆、经验资产化"四类能力仍是空白。差距的主因是**数据模型差异**：v2 的 code-map 是"双层路由索引"而非"节点-边图谱"，导致依赖图分析、跨层影响等图级能力结构性缺失。

### 3.1 v2 已定方案盘点：四大机制已吸收两条仓库核心思想

RPD v2 技术方案（内部规格 [docs/rpd-v2-technical-spec.md](docs/rpd-v2-technical-spec.md)）围绕三条主指标（M1 理解连续性 / M2 定位成本 / M3 文档引用）构建了五套机制：

1. **code-map 双层导航**：层1 router.json 常驻（≤3k token 且≤全码库 15%），层2 code-map.json 按 `function:path:name` 查单条 entry（≤300 token，从不整份喂入）。这与 Understand-Anything"扫描一次、复用多次，交互时只读相关子图"的哲学同构（[7]），也与 /understand-chat "grep 定向读取、避免整图载入上下文"的做法一致（[21]）。
2. **红线机检 + 三级信任**：code-map.meta.json 记录 map_commit + files[].fingerprint（sha256），会话启动比对 git diff map_commit..HEAD，得 verified / unverified / stale 三级。机制上与 Understand-Anything 的"git commit hash + 结构指纹"过期检测同构（[5]）。
3. **决策日志 decisions.md**：status 状态机（proposed→accepted→rejected→superseded），写入前 grill-me 拷问。
4. **审核视图五区块**：鲜度/变更/待确认/漂移/进度-代码对账，归档 review-<date>.md。
5. **产品层/代码层分层**：产品层 md 人可读可改，代码层 json 机器生成只读；R-10 兼容读取 understand-anything 的 knowledge-graph.json。

**R-10 是本章的关键承重墙**：v2 明确"探测 knowledge-graph.json，schema 匹配则只读复用"——R-10 主要吸收启发点 2（JSON 图谱可提交复用），并与启发点 1（结构层不重复解析）的结构复用思想共振，使 RPD 免于自建全量理解管线（[1]）。

> 术语约定：下文矩阵与归因中的 **P1/P2** 指 RPD v2 内部需求优先级（P0 为当前迭代必做、P1 为近期排期、P2 为远期不排期），详见规格附录 A。

### 3.4 v2 潜在薄弱点（为第四章 I0~I5 提供依据）

1. **跨会话记忆层级不足**：仅 decisions.md 单层抽象，无 L0 原始对话/决策依据留存。TencentDB Agent Memory 的 L0-L3 设计（L0 证据→L3 长期认知）已证明"高层减少阅读量、低层防失真"的价值（[13]）——v2 的决策日志缺"证据回溯"能力。
2. **检索策略单一**：code-map 定位依赖精确符号寻址（R-11），无语义检索兜底；Agent 用自然语言描述"支付重试逻辑"时无法定位。启发点 10 的 BM25+向量+RRF 是低成本补强。
3. **经验未资产化**：一次成功的需求诊断流程/PRD 模板/评审清单无法沉淀复用——行业 PRD skill 已普遍支持"澄清问题→结构化产出"的标准化（[24]、[25]），RPD 的 I 轮迭代可考虑沉淀"评审检查清单"为可复用资产。
4. **无 PRD↔代码影响分析**：改需求不知影响哪些模块，改代码不知影响哪些需求——启发点 4/5 的双向映射缺失，直接影响 M1 理解连续性与 PRD 变更闭环。其中启发点 5（业务领域视图）虽归因"范围超限"，但其"domain/flow 节点 ↔ file/function/class 节点"映射可随 R-10 复用边信息时部分吸收。
5. **数据模型未图化**：这是 4/5 类能力缺失的结构性根因。R-10 复用 knowledge-graph.json 时，应同步复用其 nodes/edges 边信息（35 种边类型，[5]），而非仅当"字典"读取。

### 小结

RPD v2 的差距不是"少抄了几个功能"，而是**数据模型定位**：当前是"双层路由索引 + 决策日志"的轻量模型，尚未达到两仓库"图 + 分层记忆 + 资产化"的成熟度。已覆盖的 4 条证明方向正确（R-10 是点睛之笔）；未覆盖的 5 条中，启发点 4（图级影响分析）与 6（分层记忆）最影响 M1/M2 主指标，建议在第四章 I4（R-09~R-14 区间）优先补强。

### 4.3 论据：I4 六条需求的两仓库机制佐证

**R-19 边信息复用**：Understand-Anything 的图谱边本身就是可查询的信息源——35 种边、8 大类别，并带权重约定（contains 1.0 / calls 0.8 / imports 0.7 / depends_on 0.6），加载时做引用完整性校验（1.3 节）；TencentDB-Agent-Memory 的索引可携带"关联关系"用于邻接跳转检索。启示：code-map 层2 可在不增加额外分析的前提下，沿既有边直接回答依赖/调用/归属三类问题。

**R-20 PRD↔代码影响分析**：Understand-Anything 的 /understand-diff 提供现成范式——`buildDiff-Context` 区分 changedNodes/affectedNodes（1-hop 边连接的依赖者）/affectedLayers/unmappedFiles，按节点复杂度、跨层边数与 blast radius 做风险分级（1.4 节）；/understand-domain 再给出"技术符号→业务语言"的聚类映射。两条机制合起来即"需求↔代码双向映射"，R-20 是其在 RPD 场景（PRD 需求，而不是 git diff）的组织（需求侧用 PRD 节点、代码侧用 file/function 节点）。

**R-21 L0-L3 分层记忆**：TencentDB-Agent-Memory 的分层记忆（第 2 章）把"短期工作/项目/团队/组织"层级的上下文分开存储、迁移与过期，避免单层膨胀；Understand-Anything 的 7 阶段流水线也刻意使用中间产物分层（scan-result/layers/tour/review 各管一层），让每一层可单独重跑（1.2 节）。R-21 把这两者的"分层"落到 RPD 记忆读取与 code-map 各层语义摘要上。

**R-22 混合检索 BM25+RRF**：纯向量检索对项目名词不敏感（符号名、文件名、版本号往往是精确词），BM25 词法通道可命中这些精确词，再以 RRF 与向量通道结果融合排序——此双路+融合做法在记忆系统中常用（第 2 章 TencentDB-Agent-Memory 检索机制）；Understand-Anything 的图谱作为第三条结构化通道（先在图上定位相关节点，再补摘要）可并行叠加。

**R-23 渐进式暴露**：Understand-Anything 强调"结构层确定性 + 语义层 LLM"分开暴露（1.1 节），以及 tour.json 按依赖拓扑做渐进学习路径（1.2 节）；f: TencentDB-Agent-Memory 的记忆读取同样讲究"按需取层、先精简后详细"。R-23 复用这套渐进原则，把 code-map 双层导航的"常驻路由/按需语义"延伸为多级渐进。

**R-25 依赖版本锁定**：Understand-Anything 的过期检测 =  git 落地 hash + 结构指纹双重机制（1.3 节）；当依赖/文件变化时，只重分析变更文件，其余复用。R-25 把"版本可信"扩展到依赖层面：快照绑定依赖清单与 commit，发现依赖漂移即提示重新生成，防止 RPD 基于过期结构图给出结论。

### 4.4 parking-lot 触发条件设计

对 parking-lot 内 5 条（R-24、R-26、R-27、R-28、R-29）设统一触发条件，避免"永久搁置"：

1. **依赖就绪**：该项所需外部能力已可用。例：R-26（ACL）依赖多租户/隔离基础设施；R-28 团队记忆依赖统一账号与共享命名空间。触发 → 升至对应 I 版本排期讨论。
2. **用户信号**：≥3 次实际用户/运营反馈明确询问相同能力（如"能不能做全库影响分析""能不能多人共用图谱"）。触发 → 提案进入下一迭代。
3. **成本/收益翻转**：onboarding 成本下降或收益上升（如图谱膨胀使 R-27 全图分析的边际成本下降）。触发：进入下一版本评估。
4. **定期复核**：每个迭代末（I4 交付后、I5 规划前）评审一次 parking-lot，更新依赖就绪信号与用户信号；不满足者延续下去，满足者升级。

任何升级必须满足"进入某个 I 需有明确需求编号 + 影响范围 + 预算评估"三要素，杜绝因"顺手"混入主线。

### 4.5 风险提示

1. **token 预算**：边信息复用与混合检索会增加单次注入内容与检索成本；对策——沿用 1.1 的双层预算（router 常驻 ≤3k、单条 code-map ≤300 token），新图检索失败时回退到原有 README/code 直读路径。
2. **向后兼容**：R-10 是只读复用 "understand-anything 的 knowledge-graph.json"——图谱 schema 升级/变更时须做版本白名单与降级处理，读旧版本生成结构不进崩溃；优先"结构层可用、语义层尽力"的降级策略。
3. **图谱膨胀与过期**：全图（尤其 >10MB）与长时间未刷新会导致检索失真；坚持 commit hash + 指纹增量（勿全量缓存）、边做引用完整性校验（引用悬挂边直接剔除并告警）。
4. **对外口径**："复用/承接 Understand-Anything 机制"仅指设计范式引用与只读数据复用，不在对外承诺中宣称"同源等价/无 gap"；parking-lot 条目不得对外披露为"已规划交付"。

| R-21 L0-L3 分层记忆 | 中高 | 中高 | 中高 | P1-c |

小结：I4 采用"**先低成本高收益、后结构性适配**"顺序——P1-a 先落地 R-22（检索精确度）与 R-19（边复用），两者改动集中在 code-map 层，风险低、见效快，为后续" 影响分析"提供精确检索与边关系基础；P1-b 再上 R-20（影响分析）、R-23（渐进暴露）与 R-25（版本锁定），其中 R-20 依赖 P1-a 的边关系质量；P1-c 承接 R-21（分层记忆），与 R-20/R-28 的长期形态联动，为第 5 章架构演进（记忆分层 + 图谱化导航）打下铺垫。parking-lot 条目按 4.4 触发条件可见、可升级。整章保持了 I0~I3 原计划不动，I4 是风险受控的第一个外扩迭代。

# 第 5 章 架构演进方向：从项目状态机到万能管理 Skill

## 5.1 论点：RPD 的终极形态是"项目级记忆 + 项目级图谱 + 经验资产化"三支柱

前四章已完成"两仓库机制拆解（1/2 章）→ 现状差距盘点（第 3 章）→ 增量需求池与 I0~I5 规划（第 4 章）"的完整论证链。本章把结论收敛到**架构演进方向**上：

RPD v2 的当前形态是"双层路由索引 + 决策日志"的轻量项目状态机（第 3 章 3.4 薄弱点）。要成为"任何项目生命周期的万能管理 Skill"，其架构应从状态机演进为**三支柱架构**：

| 支柱 | 对应机制 | 来源仓库 | 承接需求 |
|---|---|---|---|
| **项目级记忆**（Project Memory） | L0-L3 分层记忆 + 证据回溯 + 版本锁定 | TencentDB-Agent-Memory | R-21、R-25 |
| **项目级图谱**（Project Graph） | 节点-边图 + 图级影响分析 + 业务域双向映射 | Understand-Anything | R-19、R-20、R-22、R-23、R-27 |
| **经验资产化**（Skill Assets） | 流程/模板/清单沉淀为可复用 Skill + ACL | 两仓库共通 | R-24、R-26、R-28、R-29 |

三支柱不是三个独立模块，而是同一数据模型（图）上的三层视图：记忆是图的时序投影，资产是图的可复用子图，图谱本身是图的主干。这正是两仓库的共同启示——**"治理优于检索、结构优于提示"**（第 2 章 TAM 定位、第 1 章 UA"Graphs that teach"）。

## 5.2 演进路径：三阶段落地

### 阶段 A（I4 内，第 4 章已排期）——补数据模型

- 落地 R-19（边信息复用）与 R-22（混合检索）：让 code-map 从"双层路由索引"升级为"可回答依赖关系的最小图"。
- 落地 R-20（PRD↔代码影响分析）与 R-23（渐进式暴露）：在最小图上实现"改需求知影响、改代码知反查"。
- 落地 R-21（L0-L3 分层记忆）与 R-25（版本锁定）：决策日志从单层抽象升级为分层记忆，并锁依赖基线。

**阶段 A 验收标志**：M1（理解连续性）与 M2（PRD 变更闭环）主指标达到第 3 章缺口分析的预期；code-map 单条注入仍 ≤300 token（预算守卫不破）。

### 阶段 B（I5，parking-lot 升级窗口）——资产化与隔离

- R-24 经验资产化：需求诊断流程 / PRD 模板 / 评审清单沉淀为可检索、可装配的 Skill 资产（行业已有 PRD skill 生态参照，第 3 章发现 4）。
- R-26 ACL + R-28 团队记忆：从单用户走向多成员共享命名空间（触发条件见第 4 章 4.4）。

**阶段 B 验收标志**：一次成功 PRD 全流程可被第二次项目复用 ≥80% 模板内容；多成员共享记忆无越权。

### 阶段 C（远期，方向性）——万能管理 Skill 完整形态

- R-27 全图影响分析（2-hop+ 传递依赖、风险累计）与 R-29 多语言支持补齐解析覆盖。
- 从"项目生命周期"扩展为"组织级项目组合管理"：多项目图谱互链、跨项目经验检索、组合级风险视图。

**阶段 C 为方向性愿景**，不进入任何具体 I 版本排期；仅在阶段 A/B 数据模型验证成功后再评估。

## 5.3 关键架构决策（演进中的红线）

1. **数据模型优先**：第 3 章差距归因显示，8 条增量项中数据模型差异 2 条、范围超限 3 条——"图 + 分层记忆"的数据模型是先决条件，其余能力大多可在此之上自然生长。
2. **预算守卫不破**：无论演进到哪个阶段，router ≤3k / 单条 code-map ≤300 token 的双层预算（R-03/R-07）是不可突破的硬约束；新能力必须满足"渐进式暴露"原则，失败回退到 README/code 直读路径（第 4 章 4.5 风险对策）。
3. **向后兼容优先**：R-10 只读复用 knowledge-graph.json 需版本白名单 + 降级处理（第 4 章 4.5），禁止新 schema 破坏旧项目可用性。
4. **红线机检持续有效**：commit hash + 指纹增量、三级信任、红线机检（v2 既有机制）不因架构演进而弱化。

## 5.4 小结

RPD 的万能管理愿景不在"功能数量"而在"数据模型 + 记忆治理 + 资产化"三支柱的架构升级。I4 是风险受控的第一步（最小图 + 分层记忆 + 混合检索），I5 承接资产化与隔离，远期方向为组织级组合管理。演进全程以"预算守卫、向后兼容、红线机检"三条红线兜底。

### 关键发现

- 发现1：两仓库的共同底层是"图/分层数据模型"，RPD 的差距本质是数据模型定位差异而非功能缺失（承接第 3 章小结）。
- 发现2：三支柱（记忆/图谱/资产）可在一个数据模型上分层实现，避免三套独立系统的复杂度。
- 发现3：演进必须受预算守卫与向后兼容约束，"万能"不等于"全量注入"——渐进式暴露与回退路径是万能管理 Skill 的可行性前提。
- 发现4：阶段 B/C 的资产化与组织级能力是方向性目标，触发条件（第 4 章 4.4）保证其不被"顺手混入"。

### 数据摘要

- 本章未引入新来源；全部引用沿用前四章已核验来源（完整列表见文末参考文献）。
- 阶段划分与需求编号（R-19~R-29）与第 4 章完全一致；验收标志与第 4 章 ROI 排序（P1-a/b/c）对齐。

## 结论

## 一、核心结论

**结论 1：RPD v2 已吸收 12 个启发点中的 4 条，方向正确，R-10 是点睛之笔。** 经第 3 章映射矩阵逐项核对，v2 已覆盖「结构/语义分层（启发点 1）、JSON 图谱可提交复用（启发点 2）、指纹增量更新（启发点 3）、渐进式暴露（启发点 7）」四条核心设计——分别对应 code-map 双层导航、R-10 只读复用 knowledge-graph.json、红线机检 + git diff 指纹、≤3k/≤300 token 预算守卫。其中 R-10（兼容读取 Understand-Anything 的 knowledge-graph.json）使 RPD 免于自建全量理解管线，是已吸收思想中最具杠杆的一条，堪称点睛之笔。

**结论 2：差距本质是数据模型定位差异，而非功能缺失。** 第 3 章归因显示，未覆盖/半覆盖的 8 条增量项中，"图级影响分析（启发点 4）"与"L0-L3 分层记忆（启发点 6）"属数据模型差异——v2 当前是"双层路由索引 + 单层决策日志"的轻量模型，而非"节点-边图谱 + 分层记忆"的成熟模型，导致依赖遍历、跨层影响、分层记忆等图级能力结构性缺失。其余增量项多为范围超限或资源约束，可在既有数据模型上补强，不构成方向性错误。

**结论 3：演进目标为"项目级记忆 + 项目级图谱 + 经验资产化"三支柱。** 第 5 章将两仓库共同启示收敛为同一数据模型（图）上的三层视图：记忆是图的时序投影（承接 R-21/R-25）、图谱是图的主干（承接 R-19/R-20/R-22/R-23）、资产是图的可复用子图（承接 R-24/R-26/R-28/R-29）。三支柱避免三套独立系统的复杂度，是 RPD 从"项目状态机"走向"任何项目生命周期的万能管理 skill"的架构主线。

**结论 4：I4 是风险受控的第一个外扩迭代。** 第 4 章保持 I0~I3 原计划不动，将六条 P1 需求（R-19~R-23、R-25）汇入 I4，并明确 I4 不与既有交付物产生依赖；其 ROI 排序遵循"先低成本高收益、后结构性适配"原则（P1-a 先落 R-22/R-19，P1-b 再上 R-20/R-23/R-25，P1-c 承接 R-21）。parking-lot 5 条设统一触发条件（依赖就绪 / 用户信号 / 成本收益翻转 / 定期复核），杜绝"永久搁置"或"顺手混入主线"。

## 二、优化建议清单（R-19~R-29 按去向分组）

**I4（P1）—— 风险受控的下一个外扩迭代：**

- **R-19 边信息复用**：将 knowledge-graph 的 35 种边 / 8 大类及权重约定纳入 code-map 导航，使其能直接回答"谁调用 X / X 依赖谁 / X 属于哪层"，验收含业务域节点双向映射。
- **R-20 PRD↔代码变更影响分析**：复用 /understand-diff 图级影响范式（changed/affectedNodes + blast radius），实现"改需求定位受影响的代码模块并分级"与"改代码反查影响的 PRD 需求"。
- **R-21 L0-L3 分层记忆**：按工作/项目/团队等层级组织记忆的读写与过期，替代单层 decisions.md，避免单层记忆膨胀。
- **R-22 混合检索 BM25+RRF**：为 code-map 与记忆检索增加 BM25 词法 + 向量语义双路及 RRF 融合，修复纯向量对符号名/文件名不敏感问题。
- **R-23 渐进式暴露**：在既有双层导航上延伸多级渐进暴露（router 常驻、code-map 按需、深入追问才注入语义摘要），守住 token 预算。
- **R-25 依赖版本锁定**：快照绑定依赖清单 + commit hash / 指纹，检测到依赖漂移即提示重新生成图谱，避免基于过期结构作答。

**parking-lot —— 设触发条件、可见可升级：**

- **R-24 经验资产化**：把多轮 PRD 与修复结论沉淀为可复用、跨项目检索的经验资产，依赖团队记忆与权限体系先行。
- **R-26 ACL 访问控制**：对 code-map / PRD / 记忆按环境或角色做权限隔离，支撑多租户与安全边界。
- **R-27 全图影响分析**：在 R-20 基础上扩展到整图谱的 2-hop+ 传递依赖与跨层风险累计，是启发点 4 的长线完整形态。
- **R-28 团队记忆**：多成员共享的团队级记忆与统一命名空间，来自第 2 章共享记忆机制。
- **R-29 多语言支持**：扩展 code-map 解析至多编程语言（tree-sitter 多语言 grammar），承接多语言项目分析。

## 四、风险与前提

以下三项为演进全程不可突破的前提，与第 4 章 4.5、第 5 章 5.3 的红线一致：

- **预算守卫不可破**：无论演进到哪一阶段，router ≤3k token / 单条 code-map ≤300 token 的双层预算（R-03/R-07）是硬约束；新能力必须满足渐进式暴露原则，失败时回退 README/code 直读路径。
- **向后兼容优先**：R-10 只读复用 knowledge-graph.json 须做 schema 版本白名单 + 降级处理，新 schema 不得破坏旧项目可用性，坚持"结构层可用、语义层尽力"的降级策略。
- **红线机检持续有效**：commit hash + 指纹增量、三级信任（verified/unverified/stale）、红线机检（v2 既有机制）不因架构演进而弱化；map 是导航而非真相，一切"基于 map 动手"仍以 verified 为前提。
